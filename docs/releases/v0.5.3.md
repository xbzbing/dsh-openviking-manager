## 主要变更

- **托管服务的「验证连接」不再误报不可达**：托管版 OpenViking 对匿名 `/health`、`/ready` 返回 401，旧版把这次拒绝当成网络不可达，`auth_mode=api_key` 的地址填对了也一直显示「该服务地址无法访问 OpenViking」。现在匿名探测收到 401/403 后用已保存的用户 Key 重试（只带鉴权头，不带租户头），可达性与凭据问题分开呈现。（#1）
- **连接诊断分清三种凭据状态**：没有配置 Key 时提示「服务可达，但尚未配置用户 Key」，Key 不被接受时提示「服务可达，但提供的用户 Key 未获接受」，`/status` 失败但服务就绪时提示「无法确认用户 Key 是否有效」，不再把这些情况混成「未就绪」或「不可达」。`/api/v1/system/status` 接受 Key 即视为已连接；托管网关不向用户 Key 暴露 `/ready` 时，就绪检查降级为「已连接，但就绪检查未通过」。
- **内部**：一次探测共享 15 秒总预算（单请求仍 8 秒上限），预算用尽后不再发起请求，五个串行请求不会叠加成长等待；`keyRejected` 只在认证请求真实返回 401/403 时记录，网络错误不再算作 Key 被拒。

## English

- **"Verify connection" no longer calls a hosted endpoint unreachable**: a managed OpenViking answers 401 to anonymous `/health` and `/ready`, and the old probe treated that rejection as a network failure — an `auth_mode=api_key` endpoint showed "OpenViking is unreachable at this endpoint" even with the right address. The anonymous probe now retries with the stored user key on 401/403 (bearer only, no tenant headers), so reachability and credentials are reported separately. (#1)
- **Connection diagnostics separate three credential states**: with no key configured the panel says "reachable, but no user key is configured", a refused key says "reachable, but the supplied user key was not accepted", and a failing `/api/v1/system/status` over a ready service says the key could not be verified — instead of folding all three into "not ready" or "unreachable". A successful `/api/v1/system/status` now means connected; when a hosted gateway does not expose `/ready` to a user key, readiness becomes "connected, but the readiness check did not pass".
- **Internal**: one probe shares a 15-second budget (8 seconds per request), and no request is issued once it is spent, so the five sequential requests can no longer add up to a long wait; `keyRejected` is recorded only when an authenticated request really answers 401/403, so a network error is no longer reported as a refused key.
